## Implemented foundations

- Existing native C ABI extended with joypad input, reset, sample-rate queries,
  copied RGBA frames and drained stereo PCM. This is not a new emulator core.
- `lib/emu/emulation_service.dart` owns a single native session, cleans up failed
  initialization/content loading, guards operations without a session, and
  delegates frame execution/input/reset/save-state operations to that ABI.
- Local application state replaces the mock default library. Save transactions
  are serialized within each persistence-service instance.

## Failed gates / limitations

- Full Flutter suite is NOT green: `all_cores_test.dart` crashes a Flutter
  subprocess with a segmentation fault. 93 tests passed in that run; unfinished
  tests are not passes. Root cause is not established by this checkpoint.
- Full analyzer is NOT clean: warnings/info remain in test files.
- Synthetic-core checks prove ABI plumbing, not commercial game compatibility.
- The built app has NOT been verified as a playable end-to-end emulator.
- PlayerScreen and import UI still require real integration. No speaker-output,
  on-screen frame, physical-controller, or pause/resume UI claim is made.
- Session calls are synchronous native work even though `start` returns a
  Future. A single-owner worker/frame scheduler remains required before player
  integration; `async` alone does not move emulation off the UI isolate.
- Frame dimensions currently come from system geometry; dynamic-resolution
  frames need a dimensions+bytes snapshot before production rendering.
- Native core code is in-process, not sandboxed or crash-isolated in the app.
- Mobile directory resolution and hashing need native/cross-platform adapters.
- Core resolver does not yet discover the repository's staged `_libretro`
  artifacts or register installed cores with AppState on startup.
